# 解释代码

先**读**再讲,不要凭文件名猜。

1. 把相关的上下文看全:调用方是谁、被谁调用、有没有测试、`git log` 里它是怎么演变的。
   **演进历史经常比代码本身更能说明"为什么这样写"。**
2. 按这个顺序讲:
   - **一句话结论**:它解决什么问题。
   - **数据怎么流**:输入从哪来,经过哪几步,输出到哪去。
   - **为什么这么写**:能看出来的取舍(性能 / 可读性 / 兼容性 / 历史包袱)。看不出来就说"看不出原因"。
   - **注意点**:哪些地方容易踩坑、改它会影响什么。
3. 引用具体位置时要给 `文件:行号`。
4. 如果代码本身有可疑之处(死代码、重复逻辑、明显的 bug),**顺带指出来** —— 读代码时
   顺手的观察往往比专门审查更有价值。
